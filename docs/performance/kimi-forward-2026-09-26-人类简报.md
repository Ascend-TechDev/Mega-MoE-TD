# Kimi K3 fused forward 性能优化简报（2026-09-26）

## 一句话结论

把 FC1 的 wave window 从 16 改成 32，均衡用例最高提速 **6.4%**，
MAC ratio 从 **80.1% 提到 84.7%**；但 **1.8x 目标未达成**，最好 1.563x。
原因是真正的瓶颈 MTE2 被三条硬件硬约束封死，当前算子形态下无路可走。

## 做了什么

### 1. 先修好了测量工具

上一轮拿不到完整 PMU 数据，根因是系统缺一个 `libsqlite3.so` 软链，
导致 profiler 的所有解析任务静默失败。做了个本地软链绕过（不改系统），
现在能完整读出 AIC 各流水的占比，而且可以对已采集的数据重新解析、不用重跑 8 卡。

### 2. 推翻了原先的瓶颈判断

原本怀疑是 Cube 编译器双缓冲没做好。实测 PMU 否定了这个判断：

| 流水 | 占比 |
|---|---:|
| MAC（有效计算） | 80.1% |
| **MTE2（搬数据进 L1）** | **71.2%** |
| fixpipe | 2.3% |
| MTE3 / vector | ≈0 |

fixpipe 只有 2.3%、vector 完全空闲，说明双缓冲根本不是瓶颈。
真正和计算抢时间的是**搬运数据**。编译产物也佐证：IR 里 48 处内存空间标注
全是 `ub`，**一个 `l1` 都没有**。

每张卡每次 forward 要往 L1 搬 **33.8 GB**，而理论下限只要 0.65 GB，
放大了 35 倍——因为激活面板被重读 24 次、权重面板被重读 64 次。

### 3. 唯一有效的改动

wave window 决定一个核心复用同一块激活数据能跨多少行块。实测：

| wave window | 耗时 | 加速比 |
|---:|---:|---:|
| 8 | 14.725 ms | 1.425x |
| 16（原默认） | 14.214 ms | 1.475x |
| **32（新默认）** | **13.476 ms** | **1.562x** |
| 64 | 13.348 ms | 1.569x |

64 与 32 在测量噪声内，且需要整个专家放进一个 wave，所以选 32。

## 最终结果

### 非 MoonEP 均衡用例（本次目标）

| 用例 | 耗时 | 加速比 |
|---|---:|---:|
| E32 4k | 13.602 ms | 1.539x |
| E32 8k | 28.416 ms | 1.437x |
| E32 16k | 59.244 ms | 1.347x |
| E896 4k | 15.308 ms | 1.416x |
| E896 8k | 28.699 ms | 1.432x |
| E896 16k | 53.506 ms | 1.563x |

**全部未达 1.8x**，缺口 15%–25%。

### 回归检查：没有任何用例变慢

| 用例 | 改动前 | 改动后 |
|---|---:|---:|
| 偏斜裁剪 4k | 1.442x | **1.523x** |
| 偏斜裁剪 16k | 1.309x | **1.368x** |
| 偏斜非裁剪 4k | 1.444x | 1.453x |
| 偏斜非裁剪 8k | 1.516x | 1.506x |
| 偏斜非裁剪 16k | 1.492x | 1.489x |
| MoonEP 裁剪 4k/8k/16k | 2.256/2.183/2.111x | 2.226/2.123/2.112x |

负向变动最大 0.7%，都在 ±0.06 ms 的测量噪声内。MoonEP 的默认值本来就是 32，没动过。
**MoonEP 裁剪用例仍是全矩阵唯一超过 1.8x 的（2.1x 以上）。**

## 为什么到不了 1.8x

要提高 MAC ratio 就必须减少 MTE2 搬运量，三条路全部被硬件堵死：

1. **放大计算块** —— L0C（Cube 累加器）实测只有 256 KB，当前 256x256 配置**已经 100% 占满**。
   试 M256/N512 直接被编译器拒绝：`cc overflow, requires 4194304 bits while 2097152 bits available!`
   这是硬件物理上限，不是保守设置。
2. **把权重常驻 L1** —— 工具链只提供 UB→L1 的拷贝，**没有 GM→L1**；
   而且激活面板和权重面板各 1.75 MB，都放不进单核 L1。
3. **调编译器多缓冲开关** —— 全试过，现有配置已是最优。
   改 `no-limit` 或 `only-vector` 反而**慢 25%**。

另外，关于"同一个 rank 的多个专家只发一次数据 + 本地拷贝"这个想法：
我量化过，跨卡传输确实能降 **2.1–2.26 倍**（每卡省约 216 MB）。
但它**不能提高 MAC ratio**——接收行数仍然是 T×topk，本地拷贝会把行展开回来，
33.8 GB 的搬运量一个字节都不会少。所以没有实施。

## 如果要继续推进

需要放宽约束，按预期收益排序：

1. **改用 FP8 计算**（不只是 FP8 保存）：直接把搬运字节数减半，
   是唯一能大幅降低 33.8 GB 的手段；
2. 把 FC1 拆成独立 kernel，用超出当前 fused kernel 预算的分块策略；
3. 权重预排布成 L2 友好布局，降低重读的实际代价。

这三条都会突破"维持 fused triton forward 单 kernel 形态"的约束，需要决策。
